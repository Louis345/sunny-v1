Organic first: Sunny is an adaptive learning system, so code must route truth, evidence, and safety while Elli handles human conversation from live context instead of canned scripted responses. Follow [AI_DESIGN_PRINCIPLES.md](./AI_DESIGN_PRINCIPLES.md): more freedom, less constraint, more introspection. PRs must explain how the change follows or conflicts with these principles, show source evidence and tests, invite open reviewer challenges, and record learning-record checks and human acceptance at the tested revision. Record manager approval when the human requires it. The current workflow is local fixes and regression checks → committed first human test → PR with results → second human test and regression checks → explicit human merge approval. (The automatic Opus challenge step is paused; see Hard boundaries.)
Every human-caught child-session bug must become a lab invariant: explain why the human caught it, why logs did or did not catch it, and why the AI lab missed it.
Diagnose before you fix: for a human-caught bug, post the decision chain that produced it (evidence → Planner → activity settings → component) and name the earliest wrong decision, with its evidence, before any code or test. Make no edits until the human confirms the diagnosis. The regression test states the intended behavior at that layer, not the symptom. If the component did the right thing with its inputs, the component is not the fix. When intent is unclear, ask why instead of choosing the easiest change.

Required learning authority: read [`LEARNING_FEEDBACK_LOOP.md`](./LEARNING_FEEDBACK_LOOP.md) before changing learning evidence, prediction, theory, or adaptation behavior. It is the sole normative learning-loop contract.

# Sunny: rules for AI agents

Sunny is a voice-first learning companion for two girls, Reina and Ila, running as a kiosk on the family Mac (Saori). Elli is their AI companion. Old law numbers are kept in brackets because other files refer to them.

## How to work

1. **Tests first [Law 1].** Write the test, run it red, then implement until green; outside an approved autonomous milestone, report the red tests and wait for "implement". For a bug, the test states the intended behavior at the layer named in the confirmed diagnosis, not the symptom. Never skip, weaken or delete a test to get green.
2. **Stay in scope [Laws 3, 6].** One problem per commit; log unrelated discoveries in `BUGS.md` instead of fixing them. Before changing architecture, or more than two files outside an approved plan, show the plan and wait for approval.
3. **No silent failures [Law 4].** Every promise is handled and every intentional ignore is logged.
4. **Prove it in the log [Law 5].** Significant state changes log as ` 🎮 [component] [action] [result]`.
5. **Prove it before handing over [Law 7].** `npm run build` and the relevant tests must pass. Say plainly what was and was not verified, including what only a real session on Saori can prove.
6. **Treat the disease, not the symptom [Law 15]. Diagnose broadly, change narrowly.** Name the class of failure, not just this instance (for example "two copies of the same truth", or "a downstream check can veto the Planner"). Prove it with runtime evidence (a captured request, a robot run, logs, saved state), never from reading code alone. Cure it at the single narrowest point where it can be removed for good, preferring deletion and one source of truth over a new layer; one disease per change, and a cure larger than two files needs an approved plan (rule 2). Add an invariant test that fails if the whole class returns. A patch is allowed only when a child is waiting: it must be labelled as a patch, degrade safely, and link the root-cause ticket.

## Planner is the artist; the board is the canvas

The AI Planner owns the learning journey. The board is a blank canvas and its nodes are portals to activities. Code gives the Planner expressive tools and faithfully executes the accepted design; it must not become a competing educational planner.

- **Planner authority:** The Planner chooses activities, sequence, alternatives, prerequisites, convergence, labels, activity configurations and evidence relationships from the child chart and available capabilities. The existing Experience Creator owns artwork, palette, portal positions and edge geometry/styles while preserving those frozen semantics. Their outputs assemble one immutable board definition; neither adds another planning authority or production path.
- **Canvas responsibility:** Prepared spelling Teaching/successor activities are selectable without sequence locks; the authored path recommends an order. Preserve unavailable-activity checks and actual completion/evidence. Render the declared nodes, connections, choices, and arrangement; launch their bound activities and reflect truthful runtime state. Do not infer a different journey from fixed slots, delete choices, reorder activities, invent branches, or require branch-exclusive activities merely to satisfy a renderer. Different sequences through shared activities can express a meaningful choice.
- **One executable contract:** Planner tools and runtime share the same versioned contract. Check references, supported capabilities, readiness, provenance, and execution safety at the tool boundary before publication. Never silently repair educational meaning. Contract-valid designs must execute faithfully.
- **The canvas has no presentation veto (all spelling and math boards):** A painter's canvas does not reject the painter. The Planner authors the journey once, as a sequence (`opening`, optional `choice`, `closing`); code expands it into portals, paths and connections mechanically and derives planned checkpoint lineage. Planned lineage is context only; actual exposure claims come from recorded presentation and response events. The Experience Creator is Sunny's map artist and should give every board a new design: it places stops freely (no grid or prescribed lanes), names its pattern, picks a theme preset, chooses a curve and style for each path, is told the real portal sizes and the patterns of her earlier boards, may look at the real render at 1280×720 and 768×1024 at most twice before it submits, and its submission is published exactly as submitted. Code places only the portals the artist left out, on a plain logged fallback layout; a refused or unreadable artist reply publishes its last look or, without one, the plain layout. No artist failure withholds a board. Code never rejects a map for overlap, contrast or layout, never sends Planner or Creator work back for correction, and never blocks publishing. A bad map or plan is the author's fault, visible in the saved screenshots and generation report, and judged by the human.
- **Truth checks degrade one portal:** Target words must be her assigned words, evidence IDs must exist, and activity types and native configurations must be supported. A failure never regenerates anything: the board still publishes, that one portal shows "Not ready" and is passed over, and the failure is logged as ` 🎮 [board] [portal] [not-ready] reason=...`.
- **Successor continuity:** A readable successor plan cannot be rejected for duplicated board bookkeeping or canvas quality. Runtime binds activity IDs used as path stops, connects the declared paths, and resumes shared root stops once after each option. Preserve existing artwork, positions and path styling; log any missing portal placed on the plain layout. Canvas screenshots and measurements inform human review, never permission to progress. Do not buy a journey correction. Unreadable responses and academic/evidence failures remain explicit; never invent a plan or learning results. Discovery and initial math authoring retain their academic, identity and capability contracts; their drawings are also reported as authored, never rejected for presentation.
- **Elli's role:** Give Elli live displayed state, available choices, and loading facts so she can converse naturally. Code must not prescribe canned decision dialogue. Record choice as engagement evidence, separately from academic outcomes, under `LEARNING_FEEDBACK_LOOP.md`.
- **Accountability:** Wrong instructional intent belongs to the Planner; unfaithful rendering or navigation belongs to runtime; mismatched tool/runtime expectations belong to the shared contract. Diagnose the earliest responsible layer instead of blaming the Planner for implementation limits.
- **Refactor by deletion:** Replace and remove competing topology inference, cosmetic-route dropping, fixed pedagogical slot rules, and redundant adapters. Prefer net deletion in the affected production path; report what was removed, what remains, and why. Do not chase a deletion quota by removing evidence, safety, readiness, or recovery guarantees. Acceptance must compare the authored journey with the rendered and traversable journey, including a real sandbox evaluation-to-board run.

## Preserve the approved experience

Planner authority over pedagogy and composition does not authorize removing established product presentation. Preserve Sunny's illustrated Grok world, inviting portal styling, animated paths, readable landscape progression, and meaningful child agency when academically valid. Supply that brief and available artwork to the Planner; do not invent choices or enforce an activity count in the renderer. Diagnose any proposed visual downgrade and obtain explicit human agreement before changing this experience. Compare authored output and rendered kiosk screenshots to this brief before handover; geometry and unit tests alone do not establish visual quality.

## Hard boundaries

- **Human acceptance before merge.** Do not merge a PR until a human has run the relevant acceptance test, reviewed the results and reviewer approvals, and explicitly authorized merging the current PR revision. Green CI and AI reviewer approval alone are insufficient. Record the tested commit and human approval in the PR; new behavior changes require renewed human acceptance. For child-facing voice or learning changes, use the canonical visible kiosk session described below. The mechanical gate is `human-gate` (`.github/workflows/human-gate.yml`, green only after the owner comments `/ship`) plus CI (build, all tests, and the next-board robot `src/scripts/spellingNextBoardAcceptance.test.ts`). The automatic AI review (`ai-review/opus`, `.github/workflows/claude-review.yml`) is **paused since 2026-10-22** by owner decision, for cost: it re-reviewed whole PRs on every push and did not catch the bugs that running Sunny caught. Do not expect `ai-review/opus` statuses on PRs, do not wait for them, and do not re-enable the workflow unless the owner asks (`gh workflow enable "AI Review"`). Background: [`docs/PR_REVIEW_GATE.md`](./docs/PR_REVIEW_GATE.md).
- **Kiosk-only human sessions.** Start every child, parent, or Saori acceptance session through the canonical `npm run sunny:run -- ...` kiosk launcher, without `--no-browser`. Never substitute an ordinary Chrome tab or reconnect a human test through a tab. `--no-browser` is only for explicitly automated or headless verification and must never be handed to a human tester. Before saying a human session is ready, require the log invariant `🎮 [kiosk] [kiosk-visible] [confirmed]` and verify the dedicated kiosk is visible; if that invariant fails, stop and fix the kiosk launch instead of using a browser fallback.
- **Learning contract [Laws 13, 14].** `LEARNING_FEEDBACK_LOOP.md` is the only authority for the learning loop. Sunny is accountable to reality, not vibes; every activity is a measurement instrument first and a game second, and private game scores or synthetic learning claims are forbidden.
- **Child chart is the decision doorway [Law 12].** New Planner, generator, care-plan and adaptive decision code starts from `getChildChart(childId)`, never from raw profile, word-bank, homework, attempt or vitals files (low-level IO adapters for the chart excepted).
- **Math Prompt Chain Boundary:** Math has one production ingestion path: assignment and child chart → Planner → Experience Creator → Playwright runtime verification. The only AI roles are the Planner and Experience Creator. No new math production module, model call, fallback, renderer, or pipeline may be added without explicit human approval. New abstractions must replace an existing one in the same change, and math hot-path production line count must remain neutral or decrease. Code owns truth, provenance, lifecycle safety, and runtime behavior; AI owns activity count, item count, pedagogy, mechanics, themes, and response format.
- **Real children's data.** Never modify Reina's or Ila's data or charts from tests, labs or verification. No paid provider calls in verification unless the human approves them.
- **No unbounded loops [Law 2].** Recursion, listeners and polling need a proven exit and a guard, with a test that checks it.

## Autonomous milestones

When the human approves a defined milestone to run unattended (for example "finish this while I sleep"), that approval covers its files and its red-green steps without stopping at each one. It does not cover broader scope, destructive operations, publishing, or weakening child-safety or evidence rules. Use bounded attempts, preserve diagnostics, and stop with a precise blocker when credentials, providers or an unmade product decision block progress. Human-caught bugs still need a confirmed diagnosis first.
